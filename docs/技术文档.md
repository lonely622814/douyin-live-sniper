# 为你闪耀 · 抢送工具 技术文档

## 1. 目标

在指定直播间，抢到「每天 0 点第一个」或「主播开播瞬间第一个」送出「为你闪耀」。
真正要赢的是一场**到达抖音服务器的时间戳竞赛**，所以整个系统围绕两件事设计：
**把出手时刻卡准**、**把出手动作做快**。

## 2. 送礼路径（实测）

```
直播间左上角灯牌（粉丝团按钮）
  → 粉丝团面板（Lynx 动态化容器）
    → 「去参与」
      → 陪伴之旅页面（star_accompany，跨域 iframe）
        → 「点亮粉丝星（9钻）」
          → 可能弹出「确认送出该礼物」→ 「确认」
            → 送出成功（注入点亮值 +9）
```

要点：**不是礼物面板直送**。「点亮」每个直播间每天有限次，跨天恢复。

## 3. 系统架构

```
┌─────────────┐   HTTP    ┌──────────────────────────────┐
│ 控制台网页   │◄─────────►│  Python 主程序                │
│ (panel.html)│  同源校验  │  · NTP 对时 / 定时调度         │
└─────────────┘           │  · 页面 JS 常驻监听回调         │
                          └───────────┬──────────────────┘
                                      │ CDP（WebSocket，零依赖自实现）
                          ┌───────────▼──────────────────┐
                          │ Chrome（独立 profile）         │
                          │  ├ 标签1：控制台（前台）        │
                          │  └ 标签2：直播间（后台，被驱动） │
                          │       └ 注入的监听脚本 + 操作 JS │
                          └──────────────────────────────┘
```

**一个窗口两个标签**：控制台在前台给你看，直播间在后台被程序驱动，
避免"两个窗口分不清哪个能用"。

## 4. 关键技术点

### 4.1 时间基准（决定 0 点准不准）

本机时钟实测**慢约 270~800ms**（Windows 时间服务未启用），这是手动抢不到的直接原因。

- 用多台授时服务器（阿里云/腾讯云/国家授时中心/清华 TUNA）做 **SNTP 四点法**采样
- **每台服务器一票 + 按路径质量加权**的共识算法。原因：NTP 假设去回程对称，
  实际链路不对称，误差约 (去程−回程)/2，与路径长度成正比。
  实测 38ms 的源和 222ms 的源能差出 60ms，所以只取最快路径簇
- 用 `GetSystemTimePreciseAsFileTime` 取绝对时间（默认 `time.time()` 只有 ~15.6ms 粒度）
- 用 `QueryPerformanceCounter` 做单调计时，校准后全部靠秒表推算，
  即使系统中途校时跳变也不受影响
- 触发精度自检：中位 **0µs**、最大 32µs
- 时钟精度：独立标定多次极差 **5.3ms**，最终偏差 ±0.3~4ms

### 4.2 浏览器控制（零第三方依赖）

Chrome 的 DevTools 协议走 WebSocket。为了不给用户装任何包：

- `ws.py` 手写最小 WebSocket 客户端（握手/掩码/分片/ping-pong）
- `cdp.py` 自实现 CDP 会话（读线程分发命令响应与事件）

### 4.3 页面结构：三层嵌套

粉丝团面板和陪伴之旅是字节的 **Lynx 动态化容器**，结构极绕：

```
顶层文档
 └ iframe(blob:)           ← 同源
    └ <lynx-view>          ← Shadow DOM（open）
       └ DIV.page …        ← 真正的界面（X-VIEW / X-TEXT 自定义元素）
 └ iframe(bytegecko)       ← 跨域，陪伴之旅
```

**同一个位置可能叠着两个 iframe**，跨域那个在 DOM 里更靠后（压在上面）。
所以定位元素时不能只看"存不存在"，还要看是不是真的在最上层。

### 4.4 点击方式：为什么最终选了 JS

踩过的坑（按时间顺序）：

1. **CDP 注入鼠标事件** → Lynx 面板**完全不响应**
   （事件确实打到了宿主元素上，但内部不处理）
2. 改用 **Win32 SendInput**（OS 级真实鼠标）→ 能点动，但要抢前台、
   要校准坐标、窗口一动就点偏，还经常抢不到前台静默失败
3. 一度以为"Lynx 不认 JS" —— **这个判断是错的**。
   真正原因是点错了元素：点到了里面的文字节点，而不是那一层真正的按钮

**最终方案：全部用 `element.click()`。**

- 点灯牌 → 普通按钮，JS 有效
- 点「去参与」→ Lynx 面板里的 `[class*=btn]`，JS **有效**（实测）
- 点「点亮粉丝星」→ 普通页面，JS 有效，耗时 **1~4ms**
- 点二次确认 → 普通页面，JS 有效

定位策略：**先按类名找，找不到再按文字找，并向上取"按钮级"的祖先**
（不同直播间的类名完全不同：`accompany-button` vs `btn_pking`）。

### 4.5 监听：页面 JS 常驻 + 双通道推送

**为什么不能让 Python 轮询**：轮询受 Python 循环节奏限制，且要频繁往返 CDP。

**做法**：把一段监听脚本注入直播间页面，由**页面自己的 JS**：

- 每 80ms 兜底轮询一次「是否开播 / 谁送出了为你闪耀」
- **MutationObserver**：页面 DOM 一变立刻检查（40ms 节流防弹幕刷屏）
  → 发现时间从"平均 40ms、最差 80ms"降到**同一帧内**
- 状态**变化时**才推送（安装时取的基线不算变化，避免把"本来就在播"误判成"刚开播"）
- 每 5 秒一次心跳，让控制台能确认"监听确实活着"

**推送通道为什么不用 fetch**：抖音页面的 **CSP 禁止**页面往 `127.0.0.1` 发请求
（实测 `TypeError: Failed to fetch`）。改用 **CDP 的 binding 通道**——
页面直接调用一个函数把事件交给调试协议，不走网络、不受任何页面安全策略限制。

### 4.6 刷新陪伴之旅：三种方式的实测对比

| 方式 | 耗时 | 真正重拉状态？ | 备注 |
|---|---|---|---|
| cdp `Page.reload` | — | — | iframe 目标不支持（只能在顶层目标执行） |
| 页面内 `location.reload()` | 258~620ms | ✅ 完整重载 | 注：早期曾误判为"缓存恢复不刷新"，实测是会重拉的 |
| 点返回键退出 → 再点「去参与」 | 464ms+ | ✅ | 但按钮位置会漂移 70px，还得抢前台 |

**结论**：用 `location.reload()`，快且稳。

### 4.7 开播秒抢的提速（三段优化）

开播是**唯一没有预设时刻**的触发线，所以每一毫秒都要省：

| 环节 | 优化前 | 优化后 |
|---|---|---|
| 发现开播 | 40~80ms（定时轮询） | **0~16ms**（MutationObserver） |
| 刷新页面 | 285ms | **0ms**（开播不跨天，先探测按钮，可点就跳过） |
| 点击送出 | 16ms | **3.9ms** |
| **合计** | **300~600ms** | **约 18ms** |

另外还加了**提前架枪**：主播在播时程序一直把陪伴之旅开着待命，
开播瞬间不需要从头进房（省 1~2 秒）。

### 4.8 结果判定：只看「注入点亮值」

**踩过的坑**：页面上那个按钮**不刷新就不会变**——礼物送出去了它照样显示
「点亮粉丝星（9钻）」。早期拿按钮文字当成功判据，导致把成功判成失败。

**正确判据**：陪伴之旅里的「你已注入 N 点亮值」这个数字，每送一次 +9。

### 4.9 健壮性设计

| 问题 | 解法 |
|---|---|
| 页面没加载完就点灯牌（点击全部落空） | 先检测礼物容器存在，等页面真就绪再点 |
| 面板已开着时误判"没开"，点一下反而关掉 | 判断依据放宽为"存在足够大的 Lynx 面板" |
| 控制台自己也是网页，监听脚本被装到它身上 | 挑目标时优先选直播间页，排除 127.0.0.1 |
| 残留的无调试端口 Chrome 实例导致端口永远起不来 | 启动前清理同 profile 的残留进程 |
| 手动操作 / 定时 / 开播秒抢 互相打架 | 共用一把动作锁 |
| `status()` 里访问浏览器导致界面卡死 | 状态接口**只读内存**，绝不碰浏览器 |

## 5. 实测数据（2026-09-14）

```
时钟偏差         +270 ~ +800 ms（本机慢）
时钟精度         ±0.3 ~ 4.7 ms
触发精度         中位 0µs，最大 32µs
定时出手精度     26 ms（目标 13:37:00.000，实际 13:36:59.974 开始）
开面板           107 ~ 1977 ms
进陪伴之旅       数百 ms
刷新今日状态     236 ~ 780 ms
点击送出         1 ~ 16 ms
送出（含确认+校验） 3.4 ~ 3.5 s（其中校验等待 1.1s、确认等待 1.5s）
```

端到端验证：设 `13:37:00` 定时，**成功送出**（注入点亮值 45 → 54），
页面 JS 在 `13:37:00.713` 抓到了自己的送礼事件。

## 7. 安全与风险

- 控制台只监听 `127.0.0.1`；动作接口做**同源校验**（防止别的网站用简单请求诱导送礼）
- 页面 JS 上报走 binding 通道，不开放任何跨域写接口
- **风控风险**：自动化操作抖音账号存在被限流、礼物被拦、封号的可能
- 不伪造签名参数、不改设备指纹、不绕验证码

## 8. 遗留与可改进

1. **WebSocket 钩子**：直接监听页面长连接消息，理论上比页面渲染更早发现开播
   （再快 ~16ms）
2. **确认弹窗等待固定 1.5s**：可以改成"出现即点、不出现立即返回"以缩短总耗时
3. **校验等待 1.1s**：可缩短或用更轻的判据
4. **开播检测的误报**：页面短暂抖动可能造成"下播→开播"来回跳，可加去抖
5. **手机端（Android）尚未实现**
