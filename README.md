# 为你闪耀 · 抖音抢送控制台

在指定抖音直播间自动送出「为你闪耀」（9 钻礼物），抢**主播开播的第一个**和**每天 0 点的第一个**。

整条链路（进直播间 → 开灯牌 → 进陪伴之旅 → 点「点亮粉丝星」→ 点确认）**全部用页面自己的 JS 完成**：
不移动鼠标、不抢前台、不需要校准屏幕坐标，单次点击耗时 1~4 毫秒。

> ⚠️ 仅供学习自动化与浏览器调试协议（CDP）的用法。使用前请阅读文末「风险与免责」。

---

## 特性

| 能力 | 说明 |
|---|---|
| 开播秒抢 | 未开播时按你设的间隔刷新页面兜底，**判定到开播 1.6~3.5 秒**（实测区间） |
| 0 点抢第一个 | 23:59 重新进陪伴之旅，0 点整出手，卡点精度实测 26 毫秒 |
| 指定时间出手 | 支持多个时间点，如 `14:00:00, 20:30` |
| 演练模式 | 全程走一遍但不真送，不花钻 |
| 页面 JS 常驻监听 | 80ms 轮询 + MutationObserver，页面一变立刻推送事件给控制台 |
| 高精度时钟 | 多台授时服务器共识标定，把本机时钟偏差压到 ±0.3~4 毫秒 |
| 零第三方依赖 | 手写 WebSocket + CDP 客户端，只用 Python 标准库 |

## 快速开始

1. 双击 **`启动控制台.cmd`**
   第一次会自动开一个独立配置目录的 Chrome 窗口（`chrome-profile/`，和你平时用的浏览器完全隔离），
   在里面**登录一次抖音**即可，之后登录态一直保留。
2. 在控制台里填**目标直播间地址**（或点「读取当前打开的直播间」自动识别），点「保存」。
3. 按需要打开开关：**秒送模式**（开播就抢）、**定时模式**（0 点 / 指定时间）、**演练模式**（不真送）。
4. 想先确认流程通不通：点「试一次」——它会走完整个链路但不点送出。

## 界面

三列布局，右列是运行日志（占满整列高度）：

```
┌────────────────┬────────────────┐ ┌──────────────┐
│  主播状态       │  目标直播间     │ │              │
├────────────────┼────────────────┤ │   运行日志    │
│  手动操作       │  送出模式       │ │  （整列高）   │
├────────────────┴────────────────┤ │              │
│  运行状态（横排：监听状态 + 耗时） │ │              │
└─────────────────────────────────┘ └──────────────┘
```

* **主播状态**：当前直播间、是否正在开播、是否已提前架好、点亮按钮状态、今日判定、今日已注入
* **手动操作**：没开播时怎么盯（刷新方式 / 间隔）+ 打开直播间并准备好 / 立即送出 / 刷新点亮状态
* **目标直播间**：网址、读取当前直播间、常用直播间历史（带备注）
* **送出模式**：秒送模式 / 定时模式（含指定时间）/ 演练模式
* **运行状态**：横排显示监听心跳、监听频率、首发监听、已查询，下面一排是每一步耗时
* **运行日志**：`★` 是检测到开播，`✅` 送出成功，`⚠` 失败，`ℹ` 说明

窗口宽度小于 1240px 时自动变成单列往下排。

## 开播是怎么判定的

实测抖音的直播间页面**停留久了不会自己更新**（主播开播了页面还停在"未开播"），所以用了两条路：

1. **页面 JS 常驻监听**（80ms 轮询 + MutationObserver）——页面自己更新时立刻上报；
2. **定时刷新页面兜底**——没开播就按你设的间隔重新加载页面确认。

刷新这条路的时序经过专门重写：

```
未开播 → 到点刷新 → 刷新之后的整个间隔里每 70ms 判定一次 → 页面渲染出"直播中"立刻抓住
```

* 判定窗口紧贴刷新，不插任何无关动作，页面一渲染出状态就抓到；
* 刷新周期有个 **2 秒下限**：整页刷新后抖音要 1~2 秒才能渲染出状态，
  刷得比这更快页面会一直停在加载中，反而永远判不出来（实测过）；
* 实测「开播 → 判定到」= **1.6~3.5 秒**，且与开播发生在哪个时刻无关。

> 提示：刷新方式选**「普通刷新 F5」**比「强制刷新 Ctrl+F5」快 1~2 秒——
> 房间状态来自动态接口，不走缓存，普通刷新拿到的就是最新状态。

## 0 点的动作序列

| 时刻 | 动作 | 耗时 |
|---|---|---|
| 0 点前 30 秒 | NTP 对时 | — |
| 0 点前 15 秒 | 先刷新一次陪伴之旅 + 开始监听「谁第一个送出为你闪耀」 | 约 400ms |
| **00:00:00.000** | **JS 刷新页面**（重新拉当天状态） | 300~600ms |
| 按钮出现 | **JS 点「点亮粉丝星」** | **1ms** |
| 之后 1.5 秒内 | 出现二次确认就 **JS 点掉** | 1ms |

## 技术要点（踩过的坑）

* **送礼路径**：直播间左上角灯牌 → 粉丝团面板 → 「去参与」 → 陪伴之旅 →「点亮粉丝星（9钻）」。
* **点击方式**：全部 `element.click()`。早期判断「Lynx 面板不认 JS」是错的——
  当时点到的是里面的文字节点，不是真正的按钮层。正确做法：先按类名找按钮，
  找不到再按文字找、并向上取「按钮级」的祖先。
* **结果判定**：只看「注入点亮值」这个数字。页面上那个按钮**不刷新就不会变**，
  送出去了它照样显示「点亮粉丝星」，拿它当判据一定会误判。
* **监听通道**：抖音页面的 CSP 不允许往 `127.0.0.1` 发请求，所以事件走调试协议的
  binding 通道（页面直接调用一个函数），不走网络。
* **基线处理**：监听脚本安装时拿"当时的状态"当基线，避免把"本来就在播"误判成"刚开播"。
* **页面选择**：控制台自己也是个网页，程序会优先挑抖音直播间那个页面，
  绝不把监听脚本装到控制台自己身上。
* **刷新与加载的取舍**：刷新间隔的意义是"页面加载完再等多久"还是"到点就刷"，
  两种语义差别很大——本项目用后者，并且对周期设了下限（见上文）。
* **并发保护**：手动操作、0 点调度、开播秒抢共用一把锁，不会互相打架。

## 目录结构

```
.
├─ 启动控制台.cmd           # 双击启动
├─ 1_calibrate_clock.cmd    # 时钟标定 / 触发精度自检
├─ 2_network_bench.cmd      # 网络延迟与抖动测量
├─ config.example.json      # 配置模板（复制成 config.json 使用）
├─ docs/技术文档.md          # 实现细节与调试记录
├─ web/panel.html           # 控制台界面（单文件，无框架）
└─ sniper/
   ├─ app.py       # 控制器：调度、开播守候、0 点流程、动作分发
   ├─ webflow.py   # 纯 JS 动作链：开面板、进陪伴之旅、点击、刷新、监听注入
   ├─ browser.py   # Chrome 启动/接管/残留进程清理
   ├─ cdp.py       # DevTools 协议客户端
   ├─ ws.py        # 最小 WebSocket 客户端（标准库实现）
   ├─ panel.py     # 本地 HTTP 控制台服务
   ├─ clock.py / ntp.py / timebase.py   # 高精度时钟标定
   ├─ netbench.py                       # 网络延迟/抖动测量
   └─ dom.py / fansclub.py / pcflow.py / wininput.py / probe.py / warmup.py
                                        # 早期"模拟鼠标点击"路线的实验代码，
                                        # 现在主流程不用了，留作参考
```

**不会提交到仓库的**：`chrome-profile/`（浏览器登录态）、`config.json`（你的直播间与设置）、
`data/`（本机标定数据）、截图。
