# 为你闪耀 · 抖音抢送控制台

在指定抖音直播间自动送出「为你闪耀」（9 钻礼物），抢**主播开播的第一个**和**每天 0 点的第一个**。

整条链路（进直播间 → 开灯牌 → 进陪伴之旅 → 点「点亮粉丝星」→ 点确认）**全部用页面自己的 JS 完成**：
不移动鼠标、不抢前台、不需要校准屏幕坐标，单次点击耗时 1~4 毫秒。

> ⚠️ 仅供学习自动化与浏览器调试协议（CDP）的用法。使用前请阅读文末「风险与免责」。

---

## 特性

| 能力 | 说明 |
|---|---|
| 开播秒抢 | 未开播时按你设的间隔刷新页面兜底，**判定到开播 1.6~3.5 秒**（实测区间） |
| 0 点抢第一个 | 23:59 重新进陪伴之旅，0 点整出手，卡点精度实测 26 毫秒 |
| 指定时间出手 | 支持多个时间点，如 `14:00:00, 20:30` |
| 演练模式 | 全程走一遍但不真送，不花钻 |
| 页面 JS 常驻监听 | 80ms 轮询 + MutationObserver，页面一变立刻推送事件给控制台 |
| 高精度时钟 | 多台授时服务器共识标定，把本机时钟偏差压到 ±0.3~4 毫秒 |
| 零第三方依赖 | 手写 WebSocket + CDP 客户端，只用 Python 标准库 |

## 环境要求

* Windows 10/11
* **Google Chrome 或 Microsoft Edge**（都是 Chromium 内核，用同一套调试协议）
* Python 3.11+（开发环境 3.13）
* **不需要** `pip install` 任何东西

浏览器怎么选：控制台右下角「运行日志」标题栏上有个下拉框——

| 选项 | 行为 |
|---|---|
| 自动（默认） | 先找 Chrome，找不到就用 Edge |
| Google Chrome | 固定用 Chrome |
| Microsoft Edge | 固定用 Edge |
| 自定义路径… | 填任意 Chromium 浏览器的 exe（Brave、便携版 Chrome 等） |

两种浏览器**各用各的配置目录**（`chrome-profile/` 与 `edge-profile/`），互不干扰；
换浏览器等于换一个干净环境，**第一次要在新窗口里重新登录一次抖音**。
改完浏览器设置需要**重启控制台**才生效。

## 快速开始

1. 双击 **`启动控制台.cmd`**
   第一次会自动开一个独立配置目录的浏览器窗口（Chrome 用 `chrome-profile/`、Edge 用 `edge-profile/`，
   和你平时用的浏览器完全隔离），
   在里面**登录一次抖音**即可，之后登录态一直保留。
2. 在控制台里填**目标直播间地址**（或点「读取当前打开的直播间」自动识别），点「保存」。
3. 按需要打开开关：**秒送模式**（开播就抢）、**定时模式**（0 点 / 指定时间）、**演练模式**（不真送）。
4. 想先确认流程通不通：点「试一次」——它会走完整个链路但不点送出。

## 界面

三列布局，右列是运行日志（占满整列高度）：

```
┌────────────────┬────────────────┐ ┌──────────────┐
│  主播状态       │  目标直播间     │ │              │
├────────────────┼────────────────┤ │   运行日志    │
│  手动操作       │  送出模式       │ │  （整列高）   │
├────────────────┴────────────────┤ │              │
│  运行状态（横排：监听状态 + 耗时） │ │              │
└─────────────────────────────────┘ └──────────────┘
```

* **主播状态**：当前直播间、是否正在开播、是否已提前架好、点亮按钮状态、今日判定、今日已注入
* **手动操作**：两个值守开关（见下）+ 刷新方式 / 间隔 + 打开直播间并准备好 / 立即送出 / 刷新点亮状态
* **目标直播间**：网址、读取当前直播间、常用直播间历史（带备注）
* **送出模式**：秒送模式 / 定时模式（含指定时间）/ 演练模式
* **运行状态**：横排显示监听心跳、监听频率、首发监听、已查询，下面一排是每一步耗时
* **运行日志**：`★` 是检测到开播，`✅` 送出成功，`⚠` 失败，`ℹ` 说明

窗口宽度小于 1240px 时自动变成单列往下排。

### 开关一览（每个功能都有独立开关，右上角拨动）

| 开关 | 关掉之后 |
|---|---|
| **开播监听** | 完全不守候：不判定、不刷新，也不碰浏览器 |
| **页面刷新兜底** | 只靠页面里那个 80ms 的 JS 监听，永不刷新页面（零风控风险，但页面自己更新时才有效） |
| **秒送模式** | 检测到开播也只记录，不自动出手 |
| **定时模式** | 不做 0 点那条线（指定时间仍然有效） |
| **演练模式** | 打开后只走流程不真送，不花钻 |

## 开播是怎么判定的

实测抖音的直播间页面**停留久了不会自己更新**（主播开播了页面还停在"未开播"），所以用了两条路：

1. **页面 JS 常驻监听**（80ms 轮询 + MutationObserver）——页面自己更新时立刻上报；
2. **定时刷新页面兜底**——没开播就按你设的间隔重新加载页面确认。

刷新这条路的时序经过专门重写：

```
未开播 → 到点刷新 → 刷新之后的整个间隔里每 70ms 判定一次 → 页面渲染出"直播中"立刻抓住
```

* 判定窗口紧贴刷新，不插任何无关动作，页面一渲染出状态就抓到；
* 刷新周期有个 **2 秒下限**：整页刷新后抖音要 1~2 秒才能渲染出状态，
  刷得比这更快页面会一直停在加载中，反而永远判不出来（实测过）；
* 实测「开播 → 判定到」= **1.6~3.5 秒**，且与开播发生在哪个时刻无关。

> 提示：刷新方式选**「普通刷新 F5」**比「强制刷新 Ctrl+F5」快 1~2 秒——
> 房间状态来自动态接口，不走缓存，普通刷新拿到的就是最新状态。

## 出问题怎么查：诊断日志

控制台界面右下角「运行日志」旁边有个 **诊断日志** 按钮，点一下直接打开日志文件夹；
文件在 `logs/watch-YYYYMMDD.log`，**按天分文件、只留最近 7 天**，一天几 MB。

它记的不是流水账，只记"能事后对账"的东西：

```
20:31:59.263 ===== 启动 ===== 房间=... 刷新间隔=2.5s 刷新方式=普通 秒抢=True 0点=True
20:32:01.900 #1 刷新20:32:01.900 耗时2480ms 页面[未开播=1 礼物栏=0 视频=0] 心跳=0.1s前 查询38612 → 未开播
20:32:04.420 #2 刷新20:32:04.420 耗时1250ms 页面[未开播=1 礼物栏=0 视频=0] 心跳=0.1s前 查询38688 → 未开播
20:32:06.950 ★ 开播判定 #3 刷新20:32:06.800 耗时1100ms 页面[未开播=0 礼物栏=1 视频=1]
```

**一轮刷新一行**，字段含义：

| 字段 | 含义 |
|---|---|
| `#3` | 第几轮刷新 |
| `刷新20:32:06.800` | 这一轮**发起刷新的精确时刻**（毫秒） |
| `耗时1100ms` | 从发起到判定完成用了多久 |
| `页面[未开播=0 礼物栏=1 视频=1]` | 页面读到的**原始信号**：能不能看到"未开播"字样、礼物栏在不在、视频在不在播 |
| `心跳=0.1s前` | 页面 JS 监听的心跳——**它证明程序当时确实在监听**；显示"无"就是注入脚本掉了 |
| `查询38612` | 页面 JS 已经轮询了多少次 |

### 拿它怎么判断责任

假设你在另一台电脑 **00:04:29** 点了开播，程序 **00:05:30** 才判定到，翻这段日志就能直接看出是哪种情况：

* **日志里 00:04:29 前后每 2~3 秒都有一行、心跳一直正常** → 程序在正常守候，
  接着看那几行的 `页面[...]`：如果整段时间都是 `未开播=1`，说明**是抖音那个页面没把状态更新出来**，
  而刷新又是整页重载，多刷几次才拿到直播中的页面——锅在页面/网络侧，不在程序。
* **日志里出现大段空白**（比如 00:04:29 之后一分钟没有行） → 程序那段时间卡住了
  （浏览器无响应 / 页面加载卡死 / 电脑休眠），这就是程序或环境的问题，日志里的时间戳能定位到具体卡在哪一轮。
* **心跳一直显示"无"** → 注入的监听脚本掉了，那次判定只能靠刷新兜底，会慢。
* **`耗时` 特别大**（比如两三万毫秒） → 那次刷新页面加载异常慢（网络或抖音服务端卡），
  程序一直在等页面渲染完。

## 0 点的动作序列

| 时刻 | 动作 | 耗时 |
|---|---|---|
| 0 点前 30 秒 | NTP 对时 | — |
| 0 点前 15 秒 | 先刷新一次陪伴之旅 + 开始监听「谁第一个送出为你闪耀」 | 约 400ms |
| **00:00:00.000** | **JS 刷新页面**（重新拉当天状态） | 300~600ms |
| 按钮出现 | **JS 点「点亮粉丝星」** | **1ms** |
| 之后 1.5 秒内 | 出现二次确认就 **JS 点掉** | 1ms |

## 技术要点（踩过的坑）

* **送礼路径**：直播间左上角灯牌 → 粉丝团面板 → 「去参与」 → 陪伴之旅 →「点亮粉丝星（9钻）」。
* **点击方式**：全部 `element.click()`。早期判断「Lynx 面板不认 JS」是错的——
  当时点到的是里面的文字节点，不是真正的按钮层。正确做法：先按类名找按钮，
  找不到再按文字找、并向上取「按钮级」的祖先。
* **结果判定**：只看「注入点亮值」这个数字。页面上那个按钮**不刷新就不会变**，
  送出去了它照样显示「点亮粉丝星」，拿它当判据一定会误判。
* **监听通道**：抖音页面的 CSP 不允许往 `127.0.0.1` 发请求，所以事件走调试协议的
  binding 通道（页面直接调用一个函数），不走网络。
* **基线处理**：监听脚本安装时拿"当时的状态"当基线，避免把"本来就在播"误判成"刚开播"。
* **页面选择**：控制台自己也是个网页，程序会优先挑抖音直播间那个页面，
  绝不把监听脚本装到控制台自己身上。
* **刷新与加载的取舍**：刷新间隔的意义是"页面加载完再等多久"还是"到点就刷"，
  两种语义差别很大——本项目用后者，并且对周期设了下限（见上文）。
* **并发保护**：手动操作、0 点调度、开播秒抢共用一把锁，不会互相打架。

   ├─ app.py       # 控制器：调度、开播守候、0 点流程、动作分发
   ├─ webflow.py   # 纯 JS 动作链：开面板、进陪伴之旅、点击、刷新、监听注入

   ├─ cdp.py       # DevTools 协议客户端
   ├─ ws.py        # 最小 WebSocket 客户端（标准库实现）
